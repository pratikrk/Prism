## 1. Context

Sub-projects 1 (Foundation) and 2 (Orchestrator Gate-0) are complete. The pipeline stops at `awaiting_gate0` after producing a Plan; the user reviews and approves; the research chord fires — but all 3 research agents beyond `keyword` are still stubs.

This sub-project makes all 4 agents real, adds a 5th synthesis agent, delivers a complete Strategy Brief as the primary MVP deliverable, and introduces Gate-1 (brief review + approval). It also folds in lightweight semantic clustering (previously sub-project 4), eliminating a whole sub-project by making it a synthesis output rather than a separate pipeline step.

**Strategic context:** The MVP targets founders and marketers starting SEO from scratch. The Strategy Brief is the paid deliverable — a complete strategy document answering: what to write about, in what order, against which competitors, and what LLM visibility baseline exists today.

**Design reference:** `apps/web/prototype/prototype.html` — dark-first design system, Inter + JetBrains Mono, `#7c5cff` accent. All frontend components must match this design.

## 2. Goals and requirements

### 2.1 Functional requirements

- **F1** All 4 research agents are real (not stubs): keyword (already live), competitor, content audit, LLM visibility.
- **F2** A 5th `synthesis_task` fires after all 4 complete — reads all results, calls Claude, produces Content Cluster Map + Executive Summary, writes to `strategy_briefs` table.
- **F3** Research sections appear progressively in the conversation thread as each agent completes (SSE-driven).
- **F4** After synthesis, sprint job transitions to `awaiting_gate1`; the Executive Summary card appears with Gate-1 actions.
- **F5** Gate-1 actions: Approve (saves strategy seed for monitoring), Share (generates shareable link), Refine (re-runs synthesis with feedback).
- **F6** Approving at Gate-1 transitions sprint to `complete`, saves the approved strategy seed (keywords + clusters + competitors) to `strategy_briefs.status = approved`.
- **F7** Shareable link (`/share/{token}`) shows the full brief — all 6 sections — publicly, no login required, with "Generated by Prism" branding and a sign-up CTA at the bottom.
- **F8** Each research section is also a first-class sidebar page (Keywords, Competitors, Content Audit, LLM Visibility, Strategy Brief) for deep-dive navigation matching the prototype sidebar.
- **F9** The conversation thread is the primary entry surface; sidebar pages are deep-dive views of the same data.

### 2.2 Non-functional requirements

- **NF1** All existing chord-failure, SSE, and Gate-0 contracts from sub-projects 1–2 are preserved.
- **NF2** `synthesis_task` follows the same chord-failure contract as all other child tasks — catches all exceptions, never raises past the task boundary.
- **NF3** LLM visibility uses Claude probing (5 test queries) — no new external API key required for MVP. Perplexity API is a future upgrade.
- **NF4** Content audit uses DataForSEO `on_page/pages/live` — no Firecrawl dependency for MVP.
- **NF5** Synthesis Claude call is ~5–10s; it fires after finalize confirms all children are done.
- **NF6** The shareable link is generated at synthesis time (token stored); the URL is surfaced to the user only after Gate-1 approval.
- **NF7** Both frontend sessions (prototyping) and backend sessions implement against `@prism/types` exclusively — no field name invented outside the types package.

### 2.3 Out of scope

- Content generation (sub-project 5, post-launch)
- Monitoring / rank tracking (sub-project 6, post-launch)
- Billing / Stripe (sub-project 4, next after this)
- Perplexity API for LLM visibility (future upgrade)
- Firecrawl content crawl (future upgrade to content audit)
- OpenTelemetry distributed tracing

## 4. Pipeline changes

### 4.1 Before (sub-project 2)

```
chord([keyword, competitor_stub, content_audit_stub, llm_visibility_stub])
  → finalize_task → sprint complete
```

### 4.2 After (this sub-project)

```
chord([keyword, competitor, content_audit, llm_visibility])
  → finalize_task (rolls up status, then calls synthesis_task.delay())
  → synthesis_task → sprint awaiting_gate1

                                    ↓ user approves Gate-1
                              sprint complete
                              strategy_briefs.status = approved
```

### 4.3 Progressive reveal flow

```
keyword_task completes    → NOTIFY → KeywordSection appears in thread
competitor_task completes → NOTIFY → CompetitorSection appears in thread
content_audit_task        → NOTIFY → ContentAuditSection appears
llm_visibility_task       → NOTIFY → LLMVisibilitySection appears
synthesis_task completes  → NOTIFY → ExecutiveSummaryCard appears, sprint → awaiting_gate1
```

Each section is rendered by the frontend as the SSE event arrives — no waiting for all agents.

## 5. Agent implementations

### 5.1 CompetitorAgent (`app/agents/competitor.py`)

**Input:** `CompetitorInput { domain: str, competitors: list[str], intent: str }`

**Process:**
1. DataForSEO `POST /v3/dataforseo_labs/google/competitors_domain/live` for each competitor domain
2. DataForSEO `POST /v3/dataforseo_labs/google/domain_rank_overview/live` for user domain
3. Claude analyzes: which competitor keywords the user doesn't rank for, traffic gap estimate, top 10 quick-win keywords (KD < 35, volume > 200)

**Output:**
```python
class CompetitorResult(BaseModel):
    competitors: list[CompetitorSummary]
    gap_keywords: list[GapKeyword]   # keywords competitor ranks for, user doesn't
    quick_wins: list[GapKeyword]     # subset: KD<35, vol>200

class CompetitorSummary(BaseModel):
    domain: str
    estimated_traffic: int
    ranking_keywords: int
    overlap_keywords: int            # keywords both rank for

class GapKeyword(BaseModel):
    term: str
    volume: int
    kd: int
    competitor: str                  # which competitor ranks for it
    competitor_position: int
```

**Caching:** DataForSEO responses cached 24h in Redis (same pattern as KeywordAgent).

### 5.2 ContentAuditAgent (`app/agents/content_audit.py`)

**Input:** `ContentAuditInput { domain: str, intent: str }`

**Process:**
1. DataForSEO `POST /v3/on_page/task_post` → crawl up to 50 pages of the user's domain
2. Poll `POST /v3/on_page/pages` until complete (max 60s, soft fail on timeout)
3. DataForSEO `POST /v3/dataforseo_labs/google/domain_rank_overview/live` for current rankings
4. Claude analyzes: ranking pages, thin pages, missing topic coverage vs. intent

**Output:**
```python
class ContentAuditResult(BaseModel):
    pages_crawled: int
    ranking_pages: list[AuditPage]     # pages that rank for something
    thin_pages: list[AuditPage]        # low word count, no rankings
    missing_topics: list[str]          # topic areas with no coverage
    summary: str                       # 2-3 sentence Claude summary

class AuditPage(BaseModel):
    url: str
    title: str
    word_count: int | None
    top_keyword: str | None
    position: int | None
```

### 5.3 LLMVisibilityAgent (`app/agents/llm_visibility.py`)

**Input:** `LLMVisibilityInput { domain: str, intent: str, competitors: list[str] }`

**Process:**
1. Claude generates 5 target queries based on intent (e.g. "best ATS for startups", "recruiting software comparison")
2. For each query, call Claude: *"Answer this query as an AI assistant would. What tools/products would you recommend?"*
3. Check if `domain` appears in any response
4. Record which competitors are mentioned and how frequently

**Output:**
```python
class LLMVisibilityResult(BaseModel):
    queries_tested: list[str]
    brand_mentioned: bool
    mention_count: int              # across all 5 queries
    competitor_mentions: dict[str, int]  # {competitor: mention_count}
    sample_response: str            # one example query + Claude answer
    note: str                       # "Based on Claude training data as of [date]"
```

**Note:** Results are labelled as Claude training-data based. Perplexity API upgrade path is a future ticket.

### 5.4 SynthesisAgent (`app/agents/synthesis.py`)

**Input:** `SynthesisInput { plan_id: str, keyword_result: dict, competitor_result: dict, content_audit_result: dict, llm_visibility_result: dict }`

**Process:**
1. Claude reads all 4 results in a single prompt
2. Produces Content Cluster Map: 3–6 topic clusters, each with hub page title + 3–5 spoke page titles
3. Produces Executive Summary: 3–5 prioritized recommendations with rationale and estimated impact
4. Generates `share_token = str(uuid.uuid4())`
5. Writes `StrategyBrief` row to DB

**Output:**
```python
class SynthesisResult(BaseModel):
    brief_id: str
    clusters: list[ContentCluster]
    executive_summary: list[Recommendation]
    share_token: str

class ContentCluster(BaseModel):
    name: str
    hub_page: str                    # suggested hub page title
    spoke_pages: list[str]           # 3–5 spoke page titles
    target_keywords: list[str]       # top 3 keywords for this cluster
    priority: int                    # 1 = highest

class Recommendation(BaseModel):
    title: str                       # short action title
    rationale: str                   # why this matters
    estimated_impact: str            # e.g. "800 organic/mo in 90 days"
    priority: int                    # 1 = highest
```

## 6. Data model

### 6.1 New table: `strategy_briefs`

```sql
CREATE TABLE strategy_briefs (
  id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  plan_id         UUID NOT NULL REFERENCES plans(id) ON DELETE CASCADE,
  sprint_job_id   UUID NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  clusters        JSONB NOT NULL DEFAULT '[]',
  executive_summary JSONB NOT NULL DEFAULT '[]',
  share_token     TEXT UNIQUE NOT NULL,
  status          VARCHAR NOT NULL DEFAULT 'draft',   -- draft | approved
  approved_at     TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON strategy_briefs (workspace_id);
CREATE INDEX ON strategy_briefs (share_token);
```

Migration: `0004_strategy_briefs.py`

### 6.2 Updated job status transitions

```
# Sprint job (new transitions)
running          → awaiting_gate1   (synthesis_task completes)
awaiting_gate1   → complete         (user approves Gate-1)

# Full transition table
pending          → running
running          → complete | failed | complete_with_errors | awaiting_gate0 | awaiting_gate1
awaiting_gate0   → complete
awaiting_gate1   → complete
complete         → (terminal)
failed           → running
complete_with_errors → (terminal)
```

Agent results stay in `jobs.result` (existing pattern). `strategy_briefs` stores only synthesized output + approval state.

## 7. API endpoints

### 7.1 Existing (unchanged)
- `POST /workspaces/{id}/jobs` — submit goal
- `GET /workspaces/{id}/thread` — conversation thread (updated with new item types below)
- `PATCH /plans/{id}` — inline edit
- `POST /plans/{id}/approve` — Gate-0 approval
- `POST /plans/{id}/refine` — re-plan with feedback

### 7.2 New endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `POST` | `/briefs/{brief_id}/approve` | required | Gate-1 approval — sets status=approved, records approved_at |
| `POST` | `/briefs/{brief_id}/refine` | required | Re-runs synthesis with feedback text |
| `GET`  | `/share/{token}` | none | Public brief view — full brief, no auth |

**`POST /briefs/{brief_id}/approve` response:**
```json
{ "id": "uuid", "status": "approved", "share_token": "uuid", "approved_at": "iso8601" }
```

**`POST /briefs/{brief_id}/refine` body:**
```json
{ "feedback": "focus more on long-tail keywords, competitor Lever missing" }
```
Creates a new `synthesis_task` job with feedback appended to system prompt. Sprint transitions back to `running` temporarily.

**`GET /share/{token}` response:**
Full `StrategyBrief` object (same shape as thread brief item) — no auth header required. Returns 404 if token not found.

### 7.3 Updated thread endpoint

`GET /workspaces/{id}/thread` adds two new `ThreadItem` variants:

```typescript
// Section item — one per agent, appears progressively
ThreadResearchSectionItem = {
  type: 'section'
  section_type: 'keyword' | 'competitor' | 'content_audit' | 'llm_visibility'
  job_id: string
  job_status: JobStatus
  result: KeywordResult | CompetitorResult | ContentAuditResult | LLMVisibilityResult | null
}

// Brief item — appears after synthesis
ThreadBriefItem = {
  type: 'brief'
  brief_id: string
  sprint_job_id: string
  job_status: JobStatus        // awaiting_gate1 | complete
  clusters: ContentCluster[]
  executive_summary: Recommendation[]
  share_token: string | null   // null until approved
  brief_status: 'draft' | 'approved'
}
```

Full thread order for a complete run:
```
goal → plan → section:keyword → section:competitor → section:content_audit
     → section:llm_visibility → brief
```

`ThreadJobsItem` is kept in the union for backward compatibility but is superseded by `ThreadResearchSectionItem` — individual section cards replace the old aggregate job board in the thread.

## 12. Decisions log

| # | Decision | Rationale |
|---|---|---|
| D1 | Fold semantic clustering into synthesis step | Eliminates a sub-project; Claude can cluster keywords in a single pass without embeddings/HDBSCAN for MVP quality |
| D2 | LLM visibility via Claude probing, not Perplexity API | No new API key; honest labelling ("based on training data"); Perplexity upgrade is one config change later |
| D3 | Content audit via DataForSEO on-page, not Firecrawl | DataForSEO already integrated; Firecrawl adds a dependency for MVP |
| D4 | 5th synthesis_task follows same chord-failure contract | Consistency; independently retryable; synthesis failure doesn't orphan the sprint |
| D5 | `awaiting_gate1` on sprint job (not a new job type) | Mirrors Gate-0 pattern exactly; same SSE, same transition() choke-point |
| D6 | Shareable link: full brief + branding + sign-up CTA | Viral loop; full value shown to recipient; Prism gets attribution + acquisition |
| D7 | share_token generated at synthesis time, surfaced at approval | Token exists before approval so URL is stable; user doesn't see it until they approve |
| D8 | Progressive reveal inside a "Research Sprint" container card | Sections contained, not scattered; visually cohesive; collapses cleanly when complete |
| D9 | Design system from prototype.html, not new Tailwind design | Single source of visual truth; frontend session implements against prototype exactly |
| D10 | @prism/types updated first before any implementation | Both frontend and backend sessions implement against types — prevents drift |
